# 2026-03-03 実装計画: クリエイティブ取得強化（Meta広告ライブラリ）

最終更新: 2026-03-02

## 1. 背景と目標
- 現状課題: 配信クリエイティブ（特に動画）が一部取得できず、アプリ内で閲覧できない。
- 目標: 新規広告を継続取得し、広告ID単位でクリエイティブ（画像/動画）をアプリ内でライブラリ表示できる状態にする。
- 前提: Meta広告ライブラリ上には対象広告が実在することを確認済み。

## 2. 2026-03-03 事象（追跡対象）
- 事象ID: `INC-2026-03-03-CREATIVE-FETCH`
- 内容:
  - Meta広告ライブラリに存在する広告で、アプリ側でクリエイティブ未取得が発生。
  - 遷移先LPの閲覧ができないケースがある。
  - 想定では縦動画中心のはずだが、横向き動画が取得されているケースがあり整合性に疑義。
- 優先度: `P0`

## 3. 明日の実装スコープ（必須）

### 3.1 取得パイプラインの再検証（API経路）
- Meta広告ライブラリ取得処理で、`ad_id` ごとの取得成否を構造化ログに記録。
- 失敗理由をカテゴリ化:
  - `not_found_in_api`
  - `media_url_missing`
  - `download_failed`
  - `format_mismatch`
  - `blocked_or_expired`
- DB保存時に `creative_fetch_status` / `creative_fetch_reason` / `last_fetch_at` を更新。

### 3.2 ブラウザフォールバック経路（APIで取れない場合）
- 方針: Meta広告ライブラリのブラウザ表示結果と `ad_id` を照合し、クリエイティブを回収。
- 実装要件:
  - `ad_id` 一致確認を必須化（誤紐付け防止）。
  - ダウンロードファイルに `source=meta_library_browser_fallback` を付与。
  - 保存先を広告IDで一意管理（重複保存防止）。
- 運用要件:
  - API取得失敗時のみフォールバック実行（通常経路優先）。

### 3.3 「ライブラリとして使える」表示要件
- 広告詳細で以下を最低表示:
  - クリエイティブ種別（image/video）
  - 取得元（api/fallback）
  - 取得日時
  - 取得失敗理由（未取得時）
- 一覧画面で「クリエイティブ有無」のフィルタを追加し、未取得広告の再取得対象を可視化。

### 3.4 横向き動画の異常調査（必須）
- 期待値: Meta/Facebook広告は運用上、縦動画中心。
- 調査項目:
  - 動画メタデータ（width/height/aspect_ratio）の記録漏れ有無
  - サムネイル由来の誤判定（動画と画像の取り違え）
  - 取得URLの実体が変換後素材（CDN変換）になっていないか
  - 同一 `ad_id` の複数メディア混在処理ミス
- 対応:
  - 取得時にアスペクト比を算出し、`vertical/horizontal/square` を保存
  - `horizontal` 判定データは監査ログに必ず記録し、サンプルを目視確認

## 8. 継続取得精度を上げる追加設計（新規）

### 8.1 現状で「入っている」機能
- 定期実行: Celery beat / EventBridge / scheduled runner による定期クロール

- 重複排除: `external_id` ベースの重複防止
- メディア抽出: HTTP抽出 + Playwright fallback + サムネイルfallback

### 8.2 現状で「不足している」機能（明日追加対象）

- 失敗理由コードの厳密統一（抽出失敗の再現性向上）
- 取得ソース証跡（api/fallback/manual）の永続化
- クリエイティブ縦横判定の保存（`orientation`）と監査クエリ

## 9. 全体構想（プロダクト北極星）

### 9.1 目指す姿
- 本システムは「広告データ蓄積基盤 + クリエイティブライブラリ」として運用する。
- 目的は、ヒット広告を再現可能な粒度で蓄積し、実務で再利用できる知見を継続的に増やすこと。
- 当面の最優先は「ライブラリ機能の完成度最大化」であり、生成系機能は対象外とする。

### 9.2 データ優先順位（運用方針）
- 優先1: ヒット広告（高スコア・長期配信・成果兆候あり）
- 優先2: ヒットに近い広告（比較検証用）
- 優先3: 非ヒット広告は最小限（学習用サンプルのみ）
- 意思決定: 保存/再取得/解析の計算資源はヒット広告に優先配分する。

### 9.3 必須データ資産
- クリエイティブ実体: 画像/動画ファイル、種別、取得元、取得日時
- クリエイティブ構造: フック、訴求、CTA、構成、シーン情報
- 効果指標: ヒット判定、スコア内訳、継続期間、推定消化
- 遷移先情報: LP本文、構成要素、訴求軸、広告との整合性

### 9.4 禁止事項（品質原則）
- 意味不明なデモデータを主要分析・UIに混在させない。
- 参照不可/未取得のクリエイティブを「取得済み」と見せない。
- 広告ID照合なしでフォールバック素材を紐付けない。

### 9.5 段階ロードマップ
- Phase 1: 取得品質の安定化（本ドキュメントの3章・8章を実装）
- Phase 2: ヒット広告中心の再利用機能（静止画転用、動画台本/シーン抽出）
- Phase 3: ライブラリ運用強化（検索精度、閲覧体験、再取得運用、品質監査）

## 11. AWS最大火力アーキテクチャ（精度最優先）

### 11.1 全体方針
- 精度を最優先し、処理は「高速経路」と「高精度経路」の二段化で運用する。
- 高速経路で新規広告を広く取り、高精度経路でヒット広告を深く回収する。
- すべての失敗は理由コード付きで再処理キューへ送る（失敗を放置しない）。
- インフラは AWS に完全統一し、Render.com 等のPaaS依存は採用しない。
- `render_ad` という語は Meta URL の名称であり、Render.com とは無関係として扱う。

### 11.2 推奨構成（AWS）
- Orchestration: `EventBridge Scheduler` + `Step Functions`
- Queue: `SQS`（normal / retry / dlq の3層）
- Compute:
  - 軽処理: `Lambda`（メタ情報取得、軽量抽出、判定）
  - 重処理: `ECS Fargate`（Playwright、動画ダウンロード、検証）
- Storage:
  - 原本: `S3`（raw creative）
  - 配信: `CloudFront`（閲覧高速化）
  - メタデータ: `RDS PostgreSQL`
  - 検索: `OpenSearch`（ヒット広告中心の探索）
- Monitoring:
  - `CloudWatch Metrics/Logs/Alarms`
  - `X-Ray`（遅延・失敗トレース）
  - 通知: `SNS` → Slack

### 11.3 精度を上げる実装ロジック
1. 二段取得パイプライン
- Stage A（Lambda）: API取得 + `ad_id`整合チェック + 失敗理由分類
- Stage B（Fargate）: API失敗分のみ browser fallback 回収

2. 優先度キュー（ヒット重視）
- Priority P0: ヒット広告（即時再取得）
- Priority P1: ヒット近傍広告（定期再取得）
- Priority P2: 非ヒット広告（低頻度）

3. リトライ制御
- 一時失敗: exponential backoff + jitter
- 恒久失敗: 即 `failed(permanent)` としてDLQへ
- DLQは日次 replay + 手動承認 replay の二系統

4. 取得証跡の完全保存
- `creative_fetch_status/reason/source/fetched_at`
- `request_id/run_id/task_id` を全ログで連携
- S3オブジェクトにも `ad_id/source/fetched_at` メタデータ付与

5. 縦横判定の厳密化
- ffprobe で `width/height` 抽出
- `aspect_ratio` 算出、`orientation` 保存
- horizontal は自動監査キューへ転送し目視確認対象化

### 11.4 データ品質ゲート（必須）
- Gate A: `ad_id` 一致しない素材は保存禁止
- Gate B: 取得元不明（source empty）は保存禁止
- Gate C: 画像/動画の壊れURL検知で再取得キュー投入
- Gate D: 同一adの重複素材はハッシュで統合

### 11.5 SLO（最大火力モード）
- 新規広告取り込み遅延: 6時間以内
- クリエイティブ表示成功率: 95%以上
- ヒット広告の素材取得率: 98%以上
- 未取得理由の `unknown` 比率: 2%未満
- DLQ滞留: 24時間以内に解消

### 11.6 コスト制御（性能を落とさない）
- Lambda は軽処理専用に固定し、重処理をFargateへ分離
- Fargate は Spot 優先 + 重要ジョブのみ On-Demand
- S3ライフサイクル: raw長期、低参照素材は IA/Glacier へ段階移行
- OpenSearchはヒット広告中心にインデックス（全件全文検索を避ける）

### 11.7 実装順（高効果順）
1. Step Functions による Stage A/B 分離
2. 失敗理由コード統一 + DLQ replay 自動化
3. 取得証跡（source/reason/run_id）をDB/S3に反映
4. orientation 監査と horizontal 自動検査
5. OpenSearch でヒット広告探索を高速化
